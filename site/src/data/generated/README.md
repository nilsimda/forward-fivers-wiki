# Generated Data Contracts

These files are generated by local extraction scripts and the build pipeline (`scripts/extract_item_data.py` + `scripts/extract_partbreak_data.py` + `scripts/extract_hcc_carves.py` + `scripts/extract_carve_data.py` + `scripts/extract_quest_data.py` + `site/scripts/build-data.mjs`). Do not edit them by hand.

## Source Files Consumed At Build Time

- `_items-source.json` (generated from `g1_data/mhfdat.raw.bin`)
- `_partbreak-source.json` (generated from `g1_data/mhfdat.raw.bin`)
- `_hcc-carves-source.json` (generated from `g1_data/mhfdat.raw.bin`)
- `_carves-source.json` (generated from `g1_data/mhfdat.raw.bin`; consumed by `build-data.mjs` for regular carve methods)
- `_quests-source.json` (generated from `g1_data/mhfinf.raw.bin` + local `g1_data/quests/*.bin`)
- `g1_data/monster_names.json` (manual `monster_id -> monster_name` mapping consumed by `extract_partbreak_data.py` and `extract_carve_data.py`)

`g1_data` is intentionally local-only and gitignored; committed artifacts in this folder are the shareable build inputs.

## `_carves-source.json`

Flat regular-carve extraction rows from `extract_carve_data.py`.

Each row includes:

- context: `monster_id`, `monster_name`, `path` (`primary`/`secondary`), `record_index`, `rank_slot`, `rank_label` (`lr`/`hr`/`arena`/`hr100`/`gr`)
- table resolution: `dt_index`, `dt_pointer`, `record_offset`, `entry_offset`
- drop payload: `drop_index_in_table`, `percentage`, `item_id`, `item_name`
- assoc diagnostics: `association_entry_offset`, `primary_ptr`, `secondary_ptr`, `secondary_count`, `primary_num_carves`

## `items.json`

Array of core item records. This remains the canonical item metadata projection.

Each item has:

- `id`
- `slug`
- `name`
- `description` (normalized plain text alias of `descriptionPlain` for compatibility)
- `descriptionRaw` (lossless extracted value, including control tags)
- `descriptionPlain` (control tags stripped)
- `descriptionSegments` (`[{ text, colorCode }]`, where `colorCode` can be `null`)
- `rarityRaw`
- `rarityPlusOne`
- `maxStack`
- `icon`
- `iconColor`
- `buyPrice`
- `sellPrice`
- `type`

Description parsing notes:

- color control tags are parsed from patterns like `~C05` / `~C00`
- text between tags is emitted in `descriptionSegments` with active `colorCode`
- `~C00` resets to default (`colorCode: null`)
- malformed/unrecognized tag-like text is treated as plain text (fail-soft)

## `monster-drops.json`

Monster-centric drop projection used by monster pages.

- grouped by monster (`monsterId`, `monsterLabel`)
- includes `dropModes`, `ranks`, and `drops[]`
- each `drops[]` row includes source context and the dropped item

## `item-acquisition.json`

Item-centric acquisition projection keyed by stringified `itemId`.

Each entry shape:

- `itemId`
- `itemName`
- `methods[]`

`methods[]` uses strict typed variants through `methodType`:

- `capture`: includes `monsterId`, `monsterName`, `rank`, `chance`, `quantity`
- `part_break`: includes `monsterId`, `monsterName`, `partbreakType`, `rank`, `chance`, `quantity`
- `hardcore_carve`: includes `monsterId`, `monsterName`, `rank`, `chance`, `quantity`
- `carve`: includes `monsterId`, `monsterName`, `rank`, `sourceLabel`, `chance`, `quantity`

Future source types should be added as new variants rather than overloading existing ones.

## Build-Time Guardrails

`build-data.mjs` validates:

- all acquisition `itemId` values map to existing `items.json` IDs
- numeric fields parse cleanly (`chance`, `quantity`, IDs)
- known drop modes for part break source data (`capture`, `part_break`)

If a source violates these rules, the build fails fast with an explicit error.
